# Tech Spec: Audio Transcription with Deepgram

Status: Approved · 2026-08-25
Implements: [`PRD-deepgram-transcription.md`](PRD-deepgram-transcription.md)

## CLI surface

```
rec transcribe <index|filename> [--language <code>] [--out <path>]
```

- `<index|filename>` — resolved against `recordings/` exactly like `play`:
  1-based index from `rec list`, or a filename with/without the
  `recordings/` prefix.
- `--language <code>` — Deepgram language code; default `pt-BR`.
- `--out <path>` — alternate output path for the markdown file; default is the
  recording path with `.wav` replaced by `.md`
  (`recordings/NAME.wav` → `recordings/NAME.md`).
- Exit `0` on success (prints the output path to stderr), `1` on any failure
  with a one-line `transcribe: …` message on stderr, matching the style of
  `record`/`list`/`play`. Missing key:
  `transcribe: DEEPGRAM_API_KEY is not set`.

Usage text in `main.zig` gains one line:

```
  transcribe <index|filename>  Transcribe a recording to OKF markdown via Deepgram
```

## Modules

| Module | Owns |
|---|---|
| `src/transcribe.zig` | URL building, curl subprocess, response parsing |
| `src/okf.zig` | OKF frontmatter + body rendering |

Selection resolution moves from `playback.zig` into `library.zig` as a public
`resolveName(selection, entries) ?[]const u8` so `play` and `transcribe` share
one implementation. New modules are registered in `main.zig`'s test block.

## Deepgram request

One HTTP call per transcription, via `/usr/bin/curl` (`std.process.spawn` +
pipe capture, same shell-out idiom as playback's `afplay`):

```
curl -fsS -X POST \
  -H "Authorization: Token $DEEPGRAM_API_KEY" \
  -H "Content-Type: audio/wav" \
  --data-binary @recordings/NAME.wav \
  "https://api.deepgram.com/v1/listen?model=nova-3&language=pt-BR&smart_format=true&punctuate=true&utterances=true&diarize_model=latest&mip_opt_out=true"
```

- Query parameters fixed except `language`, passed verbatim.
- Non-zero curl exit or non-2xx → `transcribe: deepgram request failed (<detail>)`.
- Response captured to memory and handed to the parser; never written to disk.
- The key travels only as a child-process environment variable / header;
  it is never printed or logged.

### Response shape (subset consumed)

```json
{ "results": { "utterances": [
  { "start": 0.0,  "end": 2.1, "confidence": 0.99,
    "transcript": "Bom dia.", "speaker": 0, "words": [ ... ] }
]}}
```

Parsed with `std.json.parseFromSlice` into a minimal struct
(`results.utterances[].{start, transcript, speaker}` — unknown fields
ignored). Empty/missing `utterances` is an error, not an empty transcript:
`transcribe: no speech found in recording`. Malformed JSON is a distinct error.

## OKF output

One concept per transcript, per the
[OKF notation](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing):
YAML frontmatter (mandatory `type`, producer-chosen fields otherwise) over a
free-form markdown body; relative links cross-reference the sibling WAV.

```markdown
---
type: Recording Transcript
title: 20260825-143000
description: Transcript of recordings/20260825-143000.wav generated by Deepgram nova-3.
resource: recordings/20260825-143000.wav
tags: [recording, transcript]
timestamp: 2026-08-25T17:30:00Z
model: nova-3
language: pt-BR
duration_sec: 12.5
---
# Utterances

| start | end | speaker | text |
|-------|-----|---------|------|
| 00:00 | 00:02 | S0 | Bom dia. |
| 00:02 | 00:05 | S1 | Tudo bem? |

# Text

Bom dia. Tudo bem?
```

Rules:

- `timestamp` is the UTC instant the command ran (`gmtime_r`), ISO 8601 with
  `Z`.
- `duration_sec` comes from the WAV header via `library`'s duration parse;
  omitted when unreadable.
- Timestamps render as `HH:MM:SS` when ≥ 1 h, else `MM:SS`; speaker indices
  render as `S<n>` (Deepgram integers).
- `# Text` joins utterances with spaces (single trailing newline at EOF).
- Escaping: `|` and newlines inside transcript text are replaced (`\|`, space)
  so table rows stay well-formed; YAML strings are emitted plain, quoted only
  if they contain `:` followed by space, leading specials, or non-printables.

## Error handling

| Case | Message (stderr) | Exit |
|---|---|---|
| No key | `transcribe: DEEPGRAM_API_KEY is not set` | 1 |
| Selection miss / empty library | `transcribe: no recording matches '<sel>' (see \`rec list\`)` | 1 |
| curl spawn failure | `transcribe: cannot run curl` | 1 |
| Non-2xx / curl error | `transcribe: deepgram request failed (<stderr tail>)` | 1 |
| Malformed JSON | `transcribe: unexpected response from deepgram` | 1 |
| No utterances | `transcribe: no speech found in recording` | 1 |
| Output write failure | `transcribe: cannot write <path>` | 1 |

## Test plan (offline)

All in `zig build test`, no network:

1. **URL builder** — default language, custom `--language`, escaping of the
   base URL; parameter order stable.
2. **Response parsing** — fixture JSON (captured Deepgram shape) yields
   ordered utterance list (start, text, speaker); missing/malformed fields
   produce the specified errors.
3. **OKF rendering** — full document golden test (frontmatter order, table
   rows, `# Text` join); timestamp/duration formatting edges (`MM:SS` vs
   `HH:MM:SS`); pipe/newline escaping; duration omitted when null.
4. **Arg parsing** — `--language`/`--out` combinations, unknown flag rejection
   (usage + exit 1).
5. **Regression** — existing suites stay green; `play` selection behavior
   unchanged after the resolver move.

Live end-to-end (real key) is exercised manually by the orchestrator after
release, never in CI.
